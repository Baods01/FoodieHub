# 10 — 管理后台设计规格

> **面向**：大模型开发执行（Claude Code / 其他 AI Agent）
> **框架**：react-admin（基于 MUI Material Design）
> **原则**：完备、可用、流畅；不与主站样式统一，直接使用 react-admin 默认样式

---

## 一、概述

### 1.1 目标

为食探社平台提供一个**独立入口的管理后台**，供管理员（role=1）进行日常治理操作：处理举报、审核店铺勘误、管理用户封禁、发布公告、查看操作日志。

### 1.2 核心决策（已确认）

| 决策项 | 结论 |
|:---|:---|
| 入口方式 | 单 SPA 路由分离，`/admin/*` 子树挂载在当前 Vite 项目的 Router 上 |
| 样式 | react-admin 默认 Material Design（MUI），不与主站统一样式 |
| 登录 | `/admin/login` 独立登录页，调用 `POST /users/login` → 检查 role == 1 → 非管理员拒绝 |
| 功能范围 | 全部 5 类：仪表盘 + 用户管理 + 店铺管理 + 举报处理 + 操作日志 |
| 集成方式 | 混合模式 — 常规 CRUD（用户列表/日志/店铺）用 react-admin dataProvider；特殊操作（举报处理/封禁解封/数据概览）用自定义页面嵌入 |
| 布局 | react-admin 默认左侧菜单栏 + Dashboard 首页 |

### 1.3 技术栈增量

| 包 | 用途 | 备注 |
|:---|:---|:---|
| `react-admin` | 管理后台框架 | 内置 MUI、react-router、数据层 |
| `ra-data-simple-rest` | 或自定义 dataProvider | react-admin 提供的基础 REST dataProvider |

安装命令（后续执行）：
```bash
cd frontend
npm install react-admin
```

> react-admin v5 自带 MUI v5 和 react-router v6 依赖，无需额外安装。

## 二、路由设计

### 2.1 路由树

```
/                          → 主站（RootLayout → HomePage）
/login                     → 主站登录页
/register                  → 主站注册页
/shop/:id                  → 主站店铺详情
/profile | /favorites 等    → 主站其他页面

/admin/login               → 后台登录页（独立页面，无 Admin 壳）
/admin/*                   → 后台主体（AdminGuard → react-admin <Admin>）
  ├─ /                     → Dashboard（自定义页面）
  ├─ /users                → 用户列表（react-admin List）
  ├─ /users/:id/show       → 用户详情（react-admin Show）
  ├─ /shops                → 店铺管理列表（react-admin List）
  ├─ /shops/:id            → 店铺详情/编辑（react-admin Edit，含封禁/解封按钮）
  ├─ /complaints           → 举报处理（自定义页面）
  ├─ /edit-requests        → 店铺勘误审核（自定义页面）
  └─ /logs                 → 操作日志（react-admin List）
```

### 2.2 路由守卫逻辑

```typescript
// AdminGuard 伪代码
function AdminGuard() {
  const { isLoggedIn, role, initialized } = useAuthStore();

  if (!initialized) return <Loading />;
  if (!isLoggedIn) return <Navigate to="/admin/login" />;
  if (role !== 1) return <ForbiddenPage />;  // 普通用户访问 /admin 显示无权限

  return <AdminApp />;
}
```

### 2.3 Vite 配置（无需 multipage）

因为是单 SPA 路由分离，Vite 无需额外配置。只需在 `router/index.tsx` 添加：

```typescript
{
  path: '/admin/login',
  element: <AdminLoginPage />,
},
{
  path: '/admin/*',
  element: <AdminGuard />,
},
```

## 四、Data Provider 适配层

### 4.1 核心任务

后端返回的 FastAPI 响应格式与 react-admin 期望的格式不一致，需要封装适配层。

**后端格式**（`ResponseModel` 泛型）：
```json
{
  "code": 200,
  "message": "success",
  "data": { ... }   // 或数组
}
```

**react-admin 期望**：
```
GET /resources    → { data: [...], total: 123 }
GET /resources/:id → { data: {...} }
POST /resources   → { data: {...} }
PUT /resources/:id → { data: {...} }
```

### 4.2 适配函数设计

```typescript
// src/admin/dataProvider.ts

import { fetchUtils } from 'react-admin';
import type { DataProvider } from 'react-admin';
import apiClient from '../api/client'; // 复用现有 Axios 实例

/**
 * 把 FastAPI ResponseModel 转成 react-admin DataProvider 格式
 * - 分页字段映射：page → page, page_size → pageSize
 * - total 从后端分页响应中提取
 */
export const dataProvider: DataProvider = {
  getList: async (resource, params) => {
    const { page, perPage } = params.pagination;
    const { data: response } = await apiClient.get(`/${resource}`, {
      params: {
        page,
        page_size: perPage,
        ...params.filter, // 筛选条件直接摊平到 query
        sort_by: params.sort.field,
        sort_order: params.sort.order.toLowerCase(),
      },
    });
    // FastAPI 可能返回 { data: { items: [...], total: N } } 或 { data: [...] }
    // 需根据实际后端响应适配
    return {
      data: extractData(response.data),
      total: extractTotal(response.data),
    };
  },

  getOne: async (resource, params) => {
    const { data: response } = await apiClient.get(`/${resource}/${params.id}`);
    return { data: extractData(response.data) };
  },

  create: async (resource, params) => { /* ... */ },
  update: async (resource, params) => { /* ... */ },
  delete: async (resource, params) => { /* ... */ },
  // getMany, getManyReference, updateMany, deleteMany 视需要实现
};

// 辅助函数
function extractData(payload: any) {
  if (Array.isArray(payload)) return payload;
  if (payload?.data && Array.isArray(payload.data)) return payload.data;
  if (payload?.items) return payload.items;
  return payload?.data ?? payload;
}

function extractTotal(payload: any): number {
  return payload?.total ?? payload?.data?.total ?? payload?.count ?? 0;
}
```

### 4.3 需要 dataProvider 的 Resource

| Resource 名称 | 后端接口 | 操作 |
|:---|:---|:---|
| `admin/users` | `GET /admin/users`, `GET /admin/users/{id}` | List + Show |
| `admin/logs` | `GET /admin/logs`, `DELETE /admin/logs/{id}` | List + Delete |

### 4.4 自定义页面（不走 dataProvider）

| 页面 | 原因 |
|:---|:---|
| Dashboard | 聚合多个接口（`GET /admin/stats/overview` + `GET /complaints/admin/stats`） |
| 举报处理 | 复杂交互（查看举报详情 → 选择处理动作 → 确认执行），不是标准 CRUD |
| 店铺勘误审核 | 三种操作（approve / approve-correction / reject），需自定义按钮逻辑 |
| 店铺管理 | 需嵌入封禁/解封操作，且接口分布在不同路径（`/admin/shops/:id/ban`） |

### 5.1 后台登录页 `/admin/login`

**布局**：独立全屏页面，居中卡片，橙色主题色。

```
┌──────────────────────────────────────┐
│                                      │
│        ┌──────────────────┐          │
│        │    食探社         │          │
│        │   管理后台        │          │
│        │                  │          │
│        │ [用户名/邮箱]    │          │
│        │ [密码]           │          │
│        │ [  登 录  ]      │          │
│        │                  │          │
│        │ 仅限管理员访问    │          │
│        └──────────────────┘          │
│                                      │
└──────────────────────────────────────┘
```

**行为**：
1. 调用 `POST /users/login`（与主站同一接口）
2. 成功后调用 `GET /users/me` 获取用户信息
3. 检查 `role !== 1` → 提示 "非管理员账号，无法访问后台"，拒绝进入
4. role === 1 → 写入 authStore → 跳转 `/admin`

> 与主站 `/login` 的区别：主站登录后跳首页；后台登录页登录成功后跳 `/admin`，且加角色校验。

### 5.3 用户管理 `/admin/users`

**技术**：react-admin `<List>` + `<Show>`

**列表页**（`GET /admin/users`）：
| 列 | 来源字段 | 说明 |
|:---|:---|:---|
| ID | `id` | 数字 |
| 用户名 | `username` | 文本 |
| 邮箱 | `email` | 文本 |
| 手机号 | `phone` | 脱敏显示（138****8000） |
| 角色 | `role` | 0=普通用户 / 1=管理员，用 Chip 显示 |
| 状态 | `is_active` | true=正常 / false=已封禁，用彩色 Chip |
| 注册时间 | `created_at` | 格式化日期 |

**支持筛选**：`is_active` (布尔下拉)、用户名搜索

**详情页**（`GET /admin/users/{id}`）：
- 个人基本信息（头像、用户名、邮箱、手机、简介、注册时间）

- **操作按钮**：

  - 解封用户 → 弹出确认 Dialog → `POST /admin/users/{id}/unban?reason=...`

### 5.4 店铺管理 `/admin/shops`

**技术**：react-admin `<List>` + 自定义 `<Edit>`（嵌入封禁/解封按钮）

**列表页**（复用 `GET /shops` 接口，或后端提供 `GET /admin/shops` 若有的话；否则用公开 shops 接口，管理员可以看所有店铺包括已封禁的）：

| 列 | 字段 | 说明 |
|:---|:---|:---|
| ID | `id` | |
| 名称 | `name` | 可点击进入详情 |
| 品类 | `category` | |
| 区域 | `area` | |
| 评分 | `average_rating` | 星级 |
| 状态 | `is_active` / ban 状态 | 正常/已封禁 |
| 收藏数 | `favorite_count` | |
| 创建时间 | `created_at` | |

**行内操作**：封禁/解封按钮（dialog 确认）

**编辑页**（`PUT /shops/{id}` — 已是管理员接口）：
- 可修改店铺名称、描述、品类、区域、`is_active`（软删除）
- 封禁/解封操作（调用 `/admin/shops/{id}/ban` 和 `/admin/shops/{id}/unban`）

> 注意：`PUT /shops/{id}` 和 `POST /admin/shops/{id}/ban` 是两个独立接口。封禁不等于软删除。封禁是违规处置，`is_active=false` 是软删除（数据保留但不可见）。

**交互流程**：
1. 左侧加载 pending 举报列表，点击某条 → 右侧显示详情
2. 右侧展示举报类型（评论/店铺/图片）、举报人、被举报内容摘要、举报原因
3. 管理员选择处理动作（单选 radio）：
   - `delete_comment` — 删除评论
   - `ban_shop` — 封禁店铺
   - `remove_image` — 移除图片
   - `dismiss` — 驳回举报
4. 可填写处理说明（选填）
5. 点击「确认处理」→ `POST /complaints/{id}/handle { action: "...", result_description: "..." }`
6. 处理成功后：列表中移除该条（乐观更新），统计数字刷新

**状态筛选**：Tab 切换（pending / approved / rejected）可查看历史处理记录

### 5.7 操作日志 `/admin/logs`

**技术**：react-admin `<List>`（只读，支持筛选和导出）

**数据源**：
- 列表：`GET /admin/logs`（支持分页 + 多条件筛选）
- 导出：`GET /admin/logs/export`（下载完整列表）
- 删除单条：`DELETE /admin/logs/{id}` — 谨慎提供，仅超级管理员可用

**列表列**：

| 列 | 字段 | 说明 |
|:---|:---|:---|
| ID | `id` | |
| 操作人 | `operator_name` | |
| 操作模块 | `operation_module` | 用户管理/店铺管理/举报处理/公告管理 |
| 操作类型 | `operation_type` | 封禁/解封/审核通过/拒绝举报/发布公告 |
| 目标对象 | `target_object_type` + `target_object_id` | 如 "店铺#42" |
| 操作时间 | `created_at` | |
| 详情 | `detail` | Tooltip 或展开行显示 |

**筛选器**（放在 List 的 Filter 区）：
- 操作模块（下拉）
- 操作类型（下拉）
- 操作人 ID
- 时间范围（start_time ~ end_time）

**导出按钮**：触发 `GET /admin/logs/export`，下载 JSON/CSV

## 六、Auth 集成

### 6.1 authStore 扩展

当前 `authStore.ts` 存储 `role` 但未使用。管理后台需要：

```typescript
// authStore 中确保存储 role
interface AuthState {
  role: number;  // 0=普通用户, 1=管理员
  isAdmin: () => boolean;  // computed: role === 1
}
```

`login()` 时从后端返回的 `user.role` 写入。

### 6.2 react-admin authProvider

react-admin 要求提供 `authProvider` 对象，至少实现 `login` / `logout` / `checkAuth` / `checkError`：

```typescript
// src/admin/authProvider.ts
export const authProvider = {
  login: ({ username, password }) => {
    // 调用 loginApi → 检查 role → 成功返回 Promise.resolve() / 失败 reject
  },
  logout: () => {
    authStore.getState().logout();
    return Promise.resolve();
  },
  checkAuth: () => {
    const { isLoggedIn, role } = authStore.getState();
    return isLoggedIn && role === 1 ? Promise.resolve() : Promise.reject();
  },
  checkError: (error) => {
    if (error.status === 401) {
      authStore.getState().logout();
      return Promise.reject();
    }
    return Promise.resolve();
  },
  getPermissions: () => Promise.resolve(),
};
```

### 6.3 AuthGuard 组件

```typescript
function AdminGuard() {
  const { isLoggedIn, role, initialized } = useAuthStore();
  const location = useLocation();

  if (!initialized) return <CircularProgress />;
  if (!isLoggedIn) return <Navigate to="/admin/login" state={{ from: location }} />;
  if (role !== 1) return <ForbiddenPage />;

  return (
    <Admin
      dataProvider={dataProvider}
      authProvider={authProvider}
      dashboard={Dashboard}
      layout={AdminLayout}
    >
      {/* Resources */}
    </Admin>
  );
}
```

## 九、注意事项与风险

1. **后端接口响应格式不一致**：`GET /admin/users` 返回的 data 可能是 `{ items: [...], total: N }` 而非直接数组。dataProvider 需要根据实际情况适配，开发前先拉后端 Swagger 确认响应格式。

2. **封禁 ≠ 软删除**：`PUT /shops/{id}` 中的 `is_active` 控制软删除；`POST /admin/shops/{id}/ban` 是违规封禁。两者在模型上独立（bans 表 vs shops.is_active 字段），前端需要区分显示。

3. **react-admin v5 的 Breaking Changes**：react-admin v5 对 v4 有大量改动（MUI v5 → v6？需确认）。建议锁定版本 `react-admin@^5.0.0`。

4. **自定义页面与 react-admin 的数据交互**：自定义页面无法使用 react-admin 的 `useGetList` / `useUpdate` 等 hooks 的缓存机制（因为没有 Resource 注册）。建议自定义页面直接调 `apiClient`，用 `useState` + `useEffect` 管理状态。

5. **管理员登录与主站登录复用同一接口**：`POST /users/login` 不区分前台/后台登录。后台登录页需要额外一步：拿到 token → `GET /users/me` → 检查 role。未登录态需要合并到 authStore 统一管理。

6. **mock 数据策略**：管理后台的 mock 数据可以在 `dataProvider.ts` 中 mock，模拟后端分页、筛选行为。建议 mock 时直接用 react-admin 内置的 `ra-data-fakerest` 或手动造 JSON。
