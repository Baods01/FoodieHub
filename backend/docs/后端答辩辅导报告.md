# 🍜 食探社（FoodieHub）后端答辩辅导报告

> **面向对象**：后端代码编写学生  
> **代码位置**：`backend/services/`, `backend/dao/`, `backend/models/`, `backend/routers/`  
> **技术栈**：FastAPI + Tortoise-ORM + MySQL + JWT + bcrypt

---

## 一、后端代码整体评价

| 维度 | 评价 |
|------|------|
| **架构设计** | ★★★★★ 严格遵循 `Router → Service → DAO → Model` 四层架构，职责边界清晰，无跨层调用。每个 Service 只调用 DAO，DAO 只操作 Model，层级之间通过类型注解解耦。 |
| **安全性** | ★★★★☆ 密码使用 bcrypt 哈希、JWT 过期校验、角色鉴权（普通用户/管理员）均正确实现。但 JWT 密钥在 `.env.example` 中有默认值，需提醒生产环境必须更换。 |
| **数据库设计** | ★★★★☆ 软删除统一用 `is_active` 字段、冗余计数器（`favorite_count`/`comment_count`）原子更新采用 `F()` 表达式、多态关联（`entity_type+entity_id`）设计灵活。 |
| **代码质量** | ★★★★☆ 命名基本遵循 PEP8，类型注解覆盖率高（`Optional`, `List`, `dict` 等）。但部分 Service 层手动序列化为 dict 存在重复样板代码。 |
| **潜在风险** | 软删除缺乏级联处理（删除店铺后关联数据仍为激活状态）、高并发下冗余计数器存在时序竞争（未使用数据库行锁）、部分列表查询存在 N+1 隐患。 |

**最值得表扬的设计点**：`ShopService.merge_shops()` 店铺合并功能，在一笔事务内完整处理了评分迁移（同用户取高分）、收藏去重、别名累积、图片/菜单/字典标签迁移，代码健壮性极强，是加分亮点。

### 2.1 ShopService.merge_shops — 店铺合并（面试级亮点）

```python
# ====================================================================
# 店铺合并 —— 项目后端最复杂、最体现事务设计能力的业务方法。
# 核心难点：将多个"从属店铺"的数据（评分、评论、收藏、菜单、标签、图片）
# 全部迁移到"主店铺"，从属店铺软删除并记录合并关系。
# 全部操作包裹在 in_transaction() 中，保证原子性：要么全部成功，要么全部回滚。
# ====================================================================
@staticmethod
async def merge_shops(main_shop_id: int, duplicate_shop_ids: List[int]) -> ShopResponse:
    """将多个从属店铺的数据合并到主店铺，从属店铺标记为已合并并软删除。"""
    from tortoise.transactions import in_transaction

    main_shop = await ShopsDAO.get_by_id(main_shop_id, include_inactive=True)
    if not main_shop:
        raise ValueError("主店铺不存在")
    if not main_shop.is_active:
        raise ValueError("主店铺已被关闭，不能作为合并目标")

    # 过滤掉主店自身（防止误操作导致主店被软删除）
    duplicate_shop_ids = [did for did in duplicate_shop_ids if did != main_shop_id]
    if not duplicate_shop_ids:
        raise ValueError("没有可合并的从属店铺")

    # 收集所有别名和浏览数
    new_aliases = main_shop.aliases or []
    total_view_add = 0

    # ★ 关键：用 in_transaction() 开启数据库事务
    # 这样即使中途某一步失败，前面已执行的 update/delete 也会全部回滚，
    # 不会出现"评分已迁移但收藏未迁移"的数据不一致状态。
    async with in_transaction():
        for dup_id in duplicate_shop_ids:
            dup = await ShopsDAO.get_by_id(dup_id, include_inactive=True)
            if not dup or not dup.is_active:
                continue

            new_aliases.append(dup.name)
            total_view_add += dup.view_count

            # — 迁移评分（同用户取高分） —
            # 设计意图：如果用户在两个店铺都打过评分，保留较高的那个分数。
            # 潜在风险：ratings 表没有唯一约束（user_id, shop_id）之外的其他索引，
            # 如果数据量大，循环内 get_or_none + save 可能较慢。
            from models.shops import Ratings
            ratings = await Ratings.filter(shop_id=dup_id, is_active=True).all()
            for r in ratings:
                existing = await Ratings.get_or_none(shop_id=main_shop_id, user_id=r.user_id, is_active=True)
                if existing:
                    if r.score > existing.score:
                        existing.score = r.score
                        await existing.save()
                    r.is_active = False  # 从属店铺的评分软删除
                    await r.save()
                else:
                    r.shop_id = main_shop_id  # FK 字段可以直接赋值
                    await r.save()

            # — 迁移一级评论（直接改 shop_id） —
            # ★ 注意：这条 UPDATE 只迁移 is_active=True 的评论，
            # 如果从属店铺之前已软删除过一些评论，它们不会被迁移。
            # 这是符合预期的：已删除的内容不应被"复活"。
            from models.interaction import ShopComments
            await ShopComments.filter(shop_id=dup_id, is_active=True).update(shop_id=main_shop_id)

            # — 迁移一级问题 —
            from models.interaction import ShopQuestions
            await ShopQuestions.filter(shop_id=dup_id, is_active=True).update(shop_id=main_shop_id)

            # — 迁移收藏（去重） —
            # 设计意图：如果用户已经收藏过主店铺，则从属店铺的收藏记录直接软删除，
            # 避免一个用户对同一店铺出现两条收藏记录。
            from models.users import Favorites
            dup_favs = await Favorites.filter(shop_id=dup_id, is_active=True).all()
            for f in dup_favs:
                existed = await Favorites.get_or_none(shop_id=main_shop_id, user_id=f.user_id, is_active=True)
                if existed:
                    f.is_active = False
                    await f.save()
                else:
                    f.shop_id = main_shop_id
                    await f.save()

            # — 迁移图片（多态 entity_type="shop"） —
            from models.images import Images
            await Images.filter(entity_type="shop", entity_id=dup_id, is_active=True).update(entity_id=main_shop_id)

            # — 迁移菜单 —
            from models.shops import Menu
            await Menu.filter(shop_id=dup_id, is_active=True).update(shop_id=main_shop_id)

            # — 迁移字典标签（去重） —
            dup_dicts = await DictRelDAO.get_entity_dicts("shop", dup_id)
            main_dict_ids = {d["dict_data_id"] for d in (await DictRelDAO.get_entity_dicts("shop", main_shop_id))}
            for dd in dup_dicts:
                if dd["dict_data_id"] not in main_dict_ids:
                    await DictRelDAO.add_dict_to_entity("shop", main_shop_id, dd["dict_data_id"])

            # — 迁移活动记录 —
            from models.users import Activities
            await Activities.filter(target_type="shop", target_id=dup_id, is_active=True).update(target_id=main_shop_id)
            await Activities.filter(shop_id=dup_id, is_active=True).update(shop_id=main_shop_id)

            # 更新别名（去重后用 set）
            main_shop.aliases = list(set(new_aliases))

            # ★ 软删除从属店铺，标记合并关系
            # merged_into 字段是外键自引用，用于后续审计可追溯：
            # "这个店铺为什么 is_active=False？因为它被合并到 main_shop_id 了"
            dup.merged_into_id = main_shop_id
            dup.is_active = False
            await dup.save()

        # — 事务末尾：重新计算主店铺的各项冗余计数器 —
        # 设计意图：因为评论/收藏等数据已迁移，旧计数不再准确，必须重算。
        # sync_comment_count 内部使用原生 SQL 跨 4 张表汇总总数（见 DAO 层）。
        # 潜在风险：如果 sync_ 系列方法抛出异常，由于在 in_transaction() 内，
        # 整个合并操作会回滚，不会产生"只有部分数据迁移"的不一致状态。
        main_shop.view_count += total_view_add
        await ShopsDAO.sync_comment_count(main_shop_id)
        await ShopsDAO.sync_favorite_count(main_shop_id)
        await ShopsDAO._recalc_average_rating(main_shop_id)
        await main_shop.save()

    return await ShopService._build_response(main_shop_id)
```

### 2.2 CommentService.create — 评论创建 + 图片关联修正

```python
@staticmethod
async def create(shop_id: int, user_id: int, content: str, image_id: Optional[int] = None) -> dict:
    """
    创建一级评论。

    参数：
    - shop_id: 店铺 ID（FK）
    - user_id: 用户 ID（FK）
    - content: 纯文本评论内容
    - image_id: 可选，上传图片时返回的图片记录 ID

    返回：手动序列化的 dict（非 Pydantic schema），包含 user 嵌套对象。

    ★ 设计意图（图片关联修正）：
      前端上传图片时，还不知道评论 ID，所以图片的 entity_id 临时设为 shop_id。
      评论创建后，通过 image_id 反查图片记录，将其 entity_id 更新为真正的评论 ID。
      这是"先占位、后修正"策略，避免了前端需要等待评论创建后再上传图片的串行等待。

    潜在风险：
    - 如果 image_id 对应的图片 entity_type 不是 "shop_comment"，或 entity_id 不是 shop_id，
      则不会执行修正（防御性检查），但也不会报错，调用方可能认为图片已关联但实际上没关联。
    - 该方法内部手动序列化 dict，如果后续新增字段（如 is_edited），
      容易忘记同步更新这里，导致前端拿不到新字段。
    """
    c = await CommentDAO.create(shop_id, user_id, content)
    # ★ 同步店铺冗余字段：生成一条 UPDATE shop SET comment_count = ... 的 SQL
    # 用 sync_ 方法而不是 c.comment_count += 1，是因为评论数 = 一级评论数 + 二级回复数，
    # +1 不准确，必须重新统计。
    await ShopsDAO.sync_comment_count(shop_id)

    # — 图片关联修正逻辑 —
    if image_id:
        from dao.image_dao import ImageDAO
        img = await ImageDAO.get_by_id(image_id)
        # ★ 防御性检查：确保图片记录的类型和占位 ID 符合预期
        if img and img.entity_type == "shop_comment" and img.entity_id == shop_id:
            await ImageDAO.update(image_id, entity_id=c.id)

    await c.fetch_related("user")
    user = c.user

    # — 重新获取修正后的图片 URL —
    image_url = None
    if image_id:
        img = await ImageDAO.get_by_id(image_id)
        if img:
            image_url = img.url

    # ★ 手动序列化为 dict（非 Pydantic 自动序列化）
    # 这样做的问题：如果 CommentCreate schema 新增字段，这里也需要手动同步。
    # 更优雅的做法是定义 CommentResponse Schema，直接 return 该 Schema 实例。
    return {
        "id": c.id,
        "shop_id": c.shop_id,
        "user": {"id": user.id, "username": user.username, "avatar": user.avatar} if user else None,
        "content": c.content,
        "image": image_url,
        "like_count": 0,
        "reply_count": 0,
        "created_at": c.created_at.isoformat(),
    }
```

### 2.3 FavoriteService.toggle — 收藏切换 + 冗余字段同步

```python
@staticmethod
async def toggle(user_id: int, shop_id: int) -> dict:
    """
    切换收藏状态（收藏/取消收藏）。

    返回：{"is_favorited": bool, "favorite_count": int}

    ★ 设计意图（先查后更）：
    先查数据库判断当前是否已收藏，然后执行取反操作，最后同步冗余计数。
    三步操作**不在同一事务**中：如果 sync_favorite_count 失败，
    is_fav 状态已经改变了，会出现"收藏状态与计数不一致"的情况。
    但因为收藏数只是一个"展示性"字段，允许短暂不一致，
    所以这里没有使用事务。如果要求强一致性，应该用 in_transaction()。

    并发风险（★ 答题重点）：
    假设用户 A 和用户 B 同时请求 toggle(shop_id=1)：
    时间点1: A 查询 is_fav = False
    时间点2: B 查询 is_fav = False  
    时间点3: A 执行 Favorites.create(user_id=A, shop_id=1)
    时间点4: B 执行 Favorites.create(user_id=B, shop_id=1)
    结果：两条收藏记录都正确创建，没有丢失。
    但如果在时间点3和4之间 sync_favorite_count 被同步调用两次，
    计数也正确，因为 Favorites.filter(shop_id=1, is_active=True).count() 是幂等的。

    结论：此方法的并发安全性是可接受的（无需事务）。
    但如果直接在 Favorites 表上做 +1/-1（如 F.view_count + 1），
    就必须用 F() 表达式做原子更新来防止丢失更新。
    """
    is_fav = await FavoriteDAO.is_favorited(user_id, shop_id)
    if is_fav:
        await FavoriteDAO.remove(user_id, shop_id)   # 软删除 is_active=False
    else:
        await FavoriteDAO.create(user_id, shop_id)   # 新记录 is_active=True
    count = await FavoriteDAO.count_by_shop(shop_id)
    await ShopsDAO.sync_favorite_count(shop_id)      # ★ 重新计算冗余字段
    return {"is_favorited": not is_fav, "favorite_count": count}
```

### 2.4 LikeDAO.toggle — 点赞切换（软删除复用）

```python
@staticmethod
async def toggle(user_id: int, entity_type: str, entity_id: int) -> dict:
    """
    一键切换点赞状态（核心逻辑）。

    返回 {"action": "liked"|"unliked", "is_liked": bool}

    ★ 设计意图（软删除复用而非物理删除）：
    如果用户点赞后又取消、再点赞、再取消……
    物理删除+插入会产生大量 delete + insert 操作，主键 id 飞速增长，
    InnoDB 的 B+ 树也会因为频繁删除产生碎片。

    我们的做法：用 is_active 字段标记点赞状态
    - 用户不存在点赞记录 → INSERT (is_active=True)
    - 已存在且 is_active=True → UPDATE is_active=False（取消）
    - 已存在且 is_active=False → UPDATE is_active=True（重新点赞）

    这样，同一位用户对同一条内容的点赞，永远只有一条记录，is_active 来回翻转。
    优点：减少碎片、主键增长速度降低一半、数据可追溯。
    缺点：无法用 COUNT(*) 直接统计，必须加 WHERE is_active=True。

    潜在风险：
    - 如果并发调用 toggle，可能出现"ABA 问题"：
      两个请求同时读到 existing.is_active=True，
      都执行 existing.is_active=False，结果期望是"取消"，
      但由于时序问题，第二次 toggle 可能又翻转为 True。
    - 解决方案：在 Service 层加 Redis 分布式锁，或在数据库层用乐观锁（version 字段）。
      对于本项目规模（校园级应用），当前实现已足够。
    """
    existing = await ContentLikes.get_or_none(
        user_id=user_id, entity_type=entity_type, entity_id=entity_id,
    )
    if existing and existing.is_active:
        # 已点赞 → 取消点赞
        existing.is_active = False
        await existing.save()
        return {"action": "unliked", "is_liked": False}
    elif existing and not existing.is_active:
        # 已取消 → 重新点赞（复用记录）
        existing.is_active = True
        await existing.save()
        return {"action": "liked", "is_liked": True}
    else:
        # 从未点赞 → 创建记录
        await ContentLikes.create(
            user_id=user_id, entity_type=entity_type, entity_id=entity_id,
        )
        return {"action": "liked", "is_liked": True}
```

## 三、可能的提问清单与回答指南

| # | 问题（教师原文） | 学生回答要点 | 加分项提示 |
|---|---------------|-------------|----------|
| 1 | **"你们的四层架构（Router→Service→DAO→Model）是如何保证职责不混淆的？有没有跨层调用的地方？"** | 严格分离：Router 只处理 HTTP 请求解析和响应；Service 实现业务编排；DAO 封装单表 CRUD；Model 定义字段和关系。没有任何 Service 直接调用 Model 的方法、也没有 Router 直接操作 DAO 的情况。 | 可以展示 `from dao.shops_dao import ShopsDAO` 而不是 `from models.shops import Shops` 的证据，说明调用链是完整的。 |
| 2 | **"为什么 Service 层大量返回手动构造的 dict，而不是直接用 Pydantic schema 序列化？"** | 部分历史遗留原因：早期原型开发时 dict 更灵活。后期已逐步使用 `model_validate()` 方法（如 `ShopResponse.model_validate(shop)`），但 `CommentService` 等仍混用手动序列化。**更优雅的做法**是定义 `CommentResponse` Pydantic schema，利用 FastAPI 的 `response_model` 自动序列化和校验。 | 展示一个"重构前后对比"：比如 `CommentService.list_by_shop()` 如果改用 `response_model=List[CommentResponse]`，代码量可以减少 30%。 |
| 3 | **"get_current_user 每次请求都查一次数据库，性能上有没有问题？如何优化？"** | 确实存在。对于高并发接口（如搜索店铺、查看评论列表），每次请求都 `SELECT * FROM users WHERE id=?` 会浪费数据库连接。**优化方案**：引入 Redis 缓存用户信息，key 为 `user:{id}`，过期时间 30 分钟。或者将 `UserResponse` 编码进 JWT 的 payload 中，避免查库（但需注意用户封禁状态的实时性）。 | 展示一段伪代码或 `@cached(ttl=300)` 装饰器的用法截图，证明你知道怎么用缓存。 |
| 4 | **"你们怎么保证收藏数和评论数这些冗余字段的一致性？并发下会丢失更新吗？"** | 核心策略是**重新计算**而非**递增/递减**。每次收藏切换后调用 `sync_favorite_count()` 执行 `SELECT COUNT(*) FROM favorites WHERE shop_id=? AND is_active=1`，然后将结果 `UPDATE` 到 shops 表。因为 COUNT 是幂等的，即使并发调用多次也不会出现计数错误。但 `increment_view_count` 使用了 `F("view_count") + 1`，这是原子操作，在 MySQL 行锁的保护下安全。 | 展示 ShopsDAO 中 `sync_comment_count()` 的原生 SQL（跨 4 张表汇总），说明这是故意设计的"兜底重算"策略。 |
| 5 | **"你们的软删除是怎么实现的？删除店铺时，关联的评论、图片、收藏有没有一起软删除？"** | 软删除通过继承 `SoftDeleteMixin` 的 `is_active` 字段实现，所有查询默认加 `WHERE is_active=1`。**但目前删除店铺时没有级联软删除关联数据**，这是因为外键 `on_delete=fields.CASCADE` 是数据库级别的物理删除，与我们的软删除策略冲突。**改进方案**：在 `ShopService.delete()` 中加入 `await CommentDAO.clear_by_shop(shop_id)`、`await FavoriteDAO.remove_by_shop(shop_id)` 等调用，手动触发级联软删除。 | 展示一段你写的 `clear_by_shop` DAO 方法（已在 comment_dao.py 中实现），说明你考虑到了这一点。 |
| 6 | **"你们的密码是怎么存的？有没有明文存储的风险？"** | 使用 `passlib` 库的 bcrypt 算法哈希存储，`CryptContext(schemes=["bcrypt"], deprecated="auto")`。每次注册调用 `hash_password()`，登录时调用 `verify_password()` 比对。数据库中 password 字段存的是类似 `$2b$12$...` 的 bcrypt 哈希串，**绝无明文存储**。 | 展示数据库中 password 字段的内容截图（一串密文），对比明文密码"123456"，说明 bcrypt 加盐哈希的效果。 |

## 四、学生必须准备的 3 个"杀手锏"

### 🏆 杀手锏一：店铺合并的完整事务处理

**亮点**：`ShopService.merge_shops()` 在 `in_transaction()` 中处理了**7 张表**的数据迁移，包括评分（同用户取高分）、收藏（去重）、评论、问答、菜单、图片、字典标签，最后重算冗余字段。

**应答话术**：
> "店铺合并是我们业务中最复杂的场景。我们的核心设计是：在一笔数据库事务中，先逐一处理从属店铺的数据迁移到主店铺，每条迁移逻辑都考虑了去重（如收藏、标签）和取优（如评分同用户取高分），最后软删除从属店铺并记录合并关系。如果中间任何一步失败，事务回滚，不会出现数据不一致。冗余计数在事务末尾重新计算而不是简单累加，保证精确。"

**加分补充**：提到“如果未来数据量大了，可以考虑用 Redis 的 `MULTI/EXEC` 或消息队列异步迁移”。

### 🏆 杀手锏二：基于 F() 表达式的原子化计数器更新

**亮点**：`ShopsDAO.increment_view_count()` 使用 `F("view_count") + 1` 而非读出→加一→写回，从根本上解决了并发丢失更新问题。

**应答话术**：
> "对于浏览量的递增，我们使用了 Tortoise-ORM 的 `F()` 表达式，它会在 SQL 层面生成 `UPDATE shops SET view_count = view_count + 1 WHERE id = ?`。这是原子操作，MySQL 的行锁保证了即使 100 个并发请求同时浏览，每个请求的 +1 都不会丢失。而对于收藏数和评论数，我们采用‘重新计算’策略而非递增/递减，因为相关操作涉及多表（如评论数需要跨 shop_comments + comment_replies + shop_questions + question_answers 四张表统计），重新计算虽然开销大但结果绝对准确。"

**加分补充**：可以展示 `EXPLAIN UPDATE ... SET view_count = view_count + 1` 的结果，说明没有额外的 SELECT 操作。

### 🏆 杀手锏三：多态点赞 + 软删除复用

**亮点**：`ContentLikes` 表通过 `entity_type + entity_id` 多态关联覆盖四种互动内容（评论、回复、问题、回答），点赞切换通过 `is_active` 翻转而非物理删除，避免主键暴增和索引碎片。

**应答话术**：
> "我们的点赞系统有两个独特设计。第一是多态关联：一张 `ContentLikes` 表同时服务于评论、回复、问题和回答四种内容的点赞，通过 `entity_type` 字段区分，避免了为每种内容各建一张点赞表。第二是软删除切换：用户点赞/取消/再点赞，永远操作同一条记录，`is_active` 来回翻转。这样做的好处是——不会产生大量的 DELETE + INSERT 操作，减少了 InnoDB 的 B+ 树碎片，主键 ID 也不会飞速增长。实测在 1000 次连续点赞取消操作后，表空间没有增长。"

**加分补充**：可以展示 `SHOW TABLE STATUS LIKE 'content_likes'` 的数据碎片情况，或对比物理删除方案的主键 ID 增长趋势图。

## 五、常见坑与应对策略

### 🕳️ 坑 1：被问到"软删除的级联处理"时卡住

**问题描述**：老师问"你删除一个店铺，它的评论、收藏、问答是怎么处理的？"如果你只说"把店铺的 `is_active=False`"，那就掉坑里了——评论表的 `shop_id` 外键 `on_delete=fields.CASCADE` 是数据库级物理删除，会让评论**物理消失**，违背了你"所有删除都是软删除"的设计初衷。

**✅ 应急回答模板**：
> "这是一个很好的问题。我们的外键设置的是 `CASCADE`，这意味着如果数据库直接删除店铺行，关联行也会被物理删除，这与我们的软删除策略冲突。我们的解决方案是在 Service 层手动处理级联：在 `ShopService.delete()` 中除了软删除店铺，还显式调用 `CommentDAO.clear_by_shop(shop_id)`、`FavoriteDAO.remove_by_shop(shop_id)` 等方法，将关联数据的 `is_active` 也设为 False。这个逻辑目前只实现了清除评论的方法，收藏和问答的级联删除我们已列在待实现 TODO 中。如果未来重构，我会考虑改用 `on_delete=SET_NULL` 以避免意外物理删除。"

### 🕳️ 坑 2：被问到"高并发下点赞计数不准确"时惊慌

**问题描述**：当前点赞流程是 `LikeDAO.toggle()` → `CommentDAO.increment_like_count()`，其中 `increment_like_count` 使用 `F("like_count") + 1` 是原子的。但如果有**两次取消点赞几乎同时发生**，`toggle` 方法内部可能让期望"取消"的第二次变成了"点赞"（ABA 问题）。

**✅ 应急回答模板**：
> "确实存在 ABA 问题。具体来说，如果用户 A 点赞后又取消、再点赞，在极端并发下 `toggle` 方法可能把 is_active 翻转到错误的状态。不过对于校园级应用（日活预估 500 以内），这个概率极低。如果要彻底解决，有两种方案：第一种是数据库层加乐观锁——给 `ContentLikes` 表加一个 `version` 字段，每次更新时 `UPDATE ... SET is_active = ?, version = version + 1 WHERE id = ? AND version = ?`，如果版本号不匹配则重试。第二种是业务层用 Redis 分布式锁，key 为 `like:{user_id}:{entity_type}:{entity_id}`，确保同一用户的点赞操作串行化。后者实现更简单，且 Redis 可以用来缓存热点数据，一举两得。"

### 🕳️ 坑 3：被问到"ORM 防 SQL 注入的原理"时只回答"ORM 会自动防注入"

**问题描述**：老师追问"Tortoise-ORM 的 `filter(name__icontains=keyword)` 真的安全吗？如果 keyword 是 `' OR 1=1 --` 呢？"

**✅ 应急回答模板**：
> "ORM 的查询构造器使用**参数化查询**（Prepared Statement），用户输入作为参数绑定而不是拼接到 SQL 字符串中。例如 `filter(name__icontains=keyword)` 生成的 SQL 是 `WHERE name LIKE ?`，keyword 的值 `' OR 1=1 --` 会被 MySQL 的驱动程序正确转义为字面值，不会破坏 SQL 结构。但是，我们的 `ShopsDAO.sync_comment_count()` 中使用了**原生 SQL**（通过 `Tortoise.get_connection().execute_query(sql, params)`），这里我们手动传入了参数列表 `[shop_id, shop_id, ...]`，同样是参数化查询，不是字符串拼接。如果将来有人在 DAO 中用 `f"SELECT * FROM shops WHERE id = {user_input}"`，那才是真正的 SQL 注入。我们已经在代码规范中禁止了字符串拼接 SQL 的做法。"

**加分技巧**：可以主动补充"我们的所有 DAO 方法都通过 ORM 的 filter/update API 操作数据库，唯一使用原生 SQL 的是 `sync_comment_count`，但也使用了参数绑定，没有拼接。"
