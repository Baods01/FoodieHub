## 1. 三级模式结构

### 1.1 模式（Schema / 概念模式）

模式是数据库全部数据的逻辑结构和特征的描述，是所有用户的公共数据视图。"食探社"数据库的模式由以下 **19 张关系表**（基本表）及其约束、索引构成。

> **通用字段说明**：以下 19 张表均继承自 `BaseModel`，故每表均包含 `is_active`（软删除标记）、`created_at`（创建时间）、`updated_at`（更新时间）三个通用字段。为保持表结构完整，已显式列出。

### 1.2 外模式（External Schema）

外模式是不同用户在模式上看到的数据视图子集。在本系统中，外模式通过**数据库视图（View）**实现——每个角色拥有一组预定义的视图，视图封装了数据过滤规则（软删除过滤 `is_active=TRUE`、封禁过滤 `is_banned=FALSE`）、敏感字段遮蔽（如 `password`）以及跨表 JOIN 的预聚合。

> **说明**：以下视图的 SQL 定义基于 §1.1 中的 19 张基本表。所有视图均为只读`*`，写入操作通过应用层 DAO 函数（见 §6）对基本表直接操作。
>
> `*` 在 MySQL 中，基于多表 JOIN 的视图不可直接 UPDATE，单表视图可更新。本系统统一在 DAO 层操作基本表，视图仅供查询。

##### 视图 V2：`v_admin_pending_feedbacks` — 待处理工单视图

```sql
CREATE VIEW v_admin_pending_feedbacks AS
SELECT f.id            AS feedback_id,
       f.type          AS feedback_type,       -- complaint | edit_request
       f.target_type,                          -- shop | comment | image
       f.target_id,
       f.description   AS user_description,
       f.status,
       u.username      AS submitter_name,
       d.name          AS reason_name,         -- 来自 dict_data 的反馈原因标签

FROM feedbacks f
JOIN users u     ON f.user_id   = u.id
JOIN dict_data d ON f.reason_id = d.id
WHERE f.status   = 'pending'
  AND f.is_active = TRUE
ORDER BY f.created_at ASC;                    -- 早提交的优先处理
```

```sql
       m.is_read,
       sender.username   AS sender_name,         -- 系统消息时为 NULL
       m.related_entity_type,
       m.related_entity_id,
       m.created_at
FROM messages m
LEFT JOIN users sender ON m.sender_id = sender.id
WHERE m.is_active = TRUE;
```

##### 视图 V10：`v_public_activities` — 公开动态流

- **用途**：认证用户首页/用户主页的动态时间线，含作者名和关联店铺。
- **映射基本表**：`activities` + `users` + `shops`

```sql
CREATE VIEW v_public_activities AS
SELECT a.id         AS activity_id,
       a.type,
       a.target_type,
       a.target_id,
       a.content,
       u.username   AS user_name,
       a.shop_id,
       s.name       AS shop_name,           -- 店铺名便于前端展示
       a.created_at
FROM activities a
JOIN users u ON a.user_id = u.id
LEFT JOIN shops s ON a.shop_id = s.id AND s.is_active = TRUE
WHERE a.is_active = TRUE;
```

##### 视图 V11：`v_public_shops` — 公开店铺列表

##### 视图 V12：`v_public_menu` — 公开菜单

##### 视图 V13：`v_public_shop_ratings` — 公开评分汇总

- **用途**：未登录用户查看各店铺的评分人数与均分（聚合视图）。
- **映射基本表**：`ratings` + `shops`

```sql
CREATE VIEW v_public_shop_ratings AS

       s.name           AS shop_name,
       COUNT(*)         AS rating_count,
       ROUND(AVG(r.score), 1) AS avg_score
FROM ratings r
JOIN shops s ON r.shop_id = s.id
WHERE r.is_active = TRUE
  AND s.is_active  = TRUE
  AND s.is_banned   = FALSE
GROUP BY r.shop_id, s.name;
```

### 1.3 内模式（Internal Schema）

内模式描述数据库的物理存储结构。以下设计基于 **MySQL 8.0 + InnoDB 引擎**，与代码中 `Tortoise ORM` + `aerich` 迁移完全兼容。

---

#### 1.3.1 文件划分

##### 1.3.1.1 表空间组织

采用 **file-per-table** 模式（`innodb_file_per_table = ON`），每张表的数据和索引存储在独立的 `.ibd` 文件中。优势：

- **单表备份/恢复**：支持 `ALTER TABLE ... IMPORT TABLESPACE` 独立操作
- **碎片整理**：可对单张表执行 `OPTIMIZE TABLE`
- **空间释放**：删除表后立即释放磁盘空间，不膨胀共享表空间

**共享表空间 `ibdata1`** 仅存放数据字典和变更缓冲区（MySQL 8.0 默认已将 undo 日志分离到独立 undo 表空间），容量可控。

##### 1.3.1.2 数据文件按热度分层

根据业务访问频率和写入压力，将 19 张表划分为三个热度层级，建议放置于不同物理磁盘：

| 热度层级 | 表名 | 读写特征 | 建议存储介质 |
|:---|:---|:---|:---|
| **热点数据** | `shops`, `shop_comments`, `comment_replies`, `users`, `favorites` | 高频读写、高并发 | SSD（NVMe 优先） |
| **温数据** | `menu_items`, `ratings`, `activities`, `messages`, `dict_types`, `dict_data`, `dict_rels`, `content_likes`, `shop_questions`, `question_answers`, `view_history` | 中等频率读写 | SSD 或 高转速 HDD |
| **冷/日志数据** | `operation_logs`, `feedbacks`, `images` | 追加写入为主、查询频率低 | HDD（大容量、低成本） |

##### 1.3.1.3 目录结构规划

```
/mysql/
  ├── data/                          # datadir — 数据文件根目录
  │   ├── foodiehub_db/              # 数据库子目录
  │   │   ├── shops.ibd              # 热点
  │   │   ├── shop_comments.ibd      # 热点
  │   │   ├── users.ibd              # 热点
  │   │   ├── operation_logs.ibd     # 冷/日志（最大 .ibd）
  │   │   ├── ...（其余 14 张表）
  │   ├── ibdata1                    # 共享表空间（仅数据字典）
  │   ├── undo_001, undo_002         # undo 表空间（独立）
  │   └── ibtmp1                     # 临时表空间
  ├── log/                           # 日志文件目录（与数据分离）
  │   ├── ib_logfile0, ib_logfile1   # InnoDB redo log
```

#### 1.3.2 日志与数据库文件的放置

##### 1.3.2.1 InnoDB Redo Log

Redo log 是 InnoDB 写入性能的关键。**必须与数据文件放置于不同物理磁盘**，避免顺序写（redo log）与随机读写（数据文件）争抢 IO 带宽。

| 参数 | 建议值 | 说明 |
|:---|:---|:---|
| `innodb_log_group_home_dir` | `/mysql/log/` | 与 `datadir` 分离 |
| `innodb_log_file_size` | 512M | 课程设计阶段建议值；生产按 25% buffer pool 配置 |
| `innodb_log_files_in_group` | 2 | 默认值，循环写入 |
| `innodb_flush_log_at_trx_commit` | 2 | 课程阶段可接受每秒刷盘（生产建议为 1） |

##### 1.3.2.2 二进制日志 (Binlog)

Binlog 用于时间点恢复（PITR）和主从复制。

| 参数 | 建议值 | 说明 |
|:---|:---|:---|
| `log_bin` | `/mysql/log/mysql-bin` | binlog 文件路径前缀 |
| `binlog_format` | ROW | 行级复制保证数据一致性 |
| `expire_logs_days` | 7 | 自动清理 7 天前的 binlog，防止占满磁盘 |
| `max_binlog_size` | 500M | 单个 binlog 文件上限，超过则轮转 |

##### 1.3.2.3 错误日志与慢查询日志

| 日志类型 | 路径 | 关键参数 |
|:---|:---|:---|
| 错误日志 | `/mysql/log/error.log` | `log_error` |
| 慢查询日志 | `/mysql/log/slow-query.log` | `slow_query_log = ON`, `long_query_time = 2`（超过 2 秒记录） |

##### 1.3.2.4 备份策略

| 方式 | 命令/工具 | 频率 | 保留周期 |
|:---|:---|:---|:---|
| 逻辑全量备份 | `mysqldump --single-transaction foodiehub_db` | 每日凌晨 | 7 天 |
| Binlog 增量 | 保留最近 7 天 binlog 文件 | 实时 | 7 天 |

#### 1.3.3 索引方面的考虑

##### 1.3.3.1 聚簇索引设计

InnoDB 下所有表均为 **聚簇索引组织表（Index-Organized Table）**：主键 `id` 即为聚簇索引，数据行按 `id` 物理顺序存储。

**统一使用自增 `id` 作为聚簇索引的理由**：

| 考量 | 自增 ID | 自然主键（如 UUID） | 选择理由 |
|:---|:---|:---|:---|
| 插入性能 | ✅ 顺序追加到 B+Tree 末尾 | ❌ 随机插入导致页分裂 | 自增避免页分裂，写入吞吐高 |
| 空间占用 | INT (4B) / BIGINT (8B) | VARCHAR (36B) | 聚簇索引键会冗余到所有二级索引 |
| 二级索引大小 | 二级索引叶子存 8B 主键值 | 二级索引叶子存 36B 自然键 | 自增 ID 使所有辅助索引更紧凑 |

##### 1.3.3.2 辅助索引清单

以下 16 个辅助索引均来源于模型代码中的 `Meta.indexes` 声明，按表分组列出：

| 表 | 索引名 | 索引列 | 覆盖的查询模式 |
|:---|:---|:---|:---|
| `shop_comments` | `idx_comments_shop_time` | (shop_id, created_at) | `WHERE shop_id=? ORDER BY created_at DESC` — 店铺评论时间线 |
| `comment_replies` | `idx_replies_comment_time` | (comment_id, created_at) | `WHERE comment_id=? ORDER BY created_at` — 评论下回复列表 |
| `shop_questions` | `idx_questions_shop_time` | (shop_id, created_at) | `WHERE shop_id=? ORDER BY created_at DESC` — 店铺问题时间线 |
| `question_answers` | `idx_answers_question_time` | (question_id, created_at) | `WHERE question_id=? ORDER BY created_at` — 问题下回答列表 |
| `favorites` | `idx_favorites_user_time` | (user_id, created_at) | `WHERE user_id=? AND is_active=TRUE ORDER BY created_at DESC` — 用户收藏时间线 |
| `activities` | `idx_activities_user_time` | (user_id, created_at) | `WHERE user_id=? ORDER BY created_at DESC` — 用户动态时间线 |
| `messages` | `idx_messages_recipient_time` | (recipient_id, created_at) | `WHERE recipient_id=? ORDER BY created_at DESC` — 收件箱时间线 |
| `feedbacks` | `idx_feedbacks_status_time` | (status, created_at) | `WHERE status='pending' ORDER BY created_at ASC` — 管理员待处理工单 |
| `feedbacks` | `idx_feedbacks_target` | (target_type, target_id) | `WHERE target_type=? AND target_id=?` — 查某实体被举报记录 |
| `images` | `idx_images_entity` | (entity_type, entity_id) | `WHERE entity_type=? AND entity_id=?` — 查某实体的图片 |
| `dict_rels` | `idx_dict_rel_entity` | (entity_type, entity_id) | `WHERE entity_type=? AND entity_id=?` — 查某实体的标签 |
| `content_likes` | `idx_likes_entity` | (entity_type, entity_id) | `WHERE entity_type=? AND entity_id=? AND is_active=TRUE` — 查某内容点赞列表 |
| `content_likes` | `idx_likes_user_entity_time` | (user_id, entity_type, entity_id, created_at) | `WHERE user_id=? AND entity_type=? AND entity_id=?` — 判断用户是否点赞 |
| `operation_logs` | `idx_oplog_operator_time` | (operator_id, created_at) | `WHERE operator_id=? ORDER BY created_at DESC` — 用户操作审计 |
| `operation_logs` | `idx_oplog_action_time` | (action, created_at) | `WHERE action=? AND created_at BETWEEN ? AND ?` — 按动作类型统计 |
| `operation_logs` | `idx_oplog_target` | (target_type, target_id) | `WHERE target_type=? AND target_id=?` — 对象变更历史 |

##### 1.3.3.3 覆盖索引分析

部分复合索引可**覆盖查询的全部列**，无需回表（Using index），性能最佳：

| 索引 | 可覆盖的典型查询 | 覆盖说明 |
|:---|:---|:---|
| `idx_comments_shop_time` | `SELECT id, created_at FROM shop_comments WHERE shop_id=?` | 索引含 (shop_id, created_at)，id 是聚簇键自动包含 |
| `idx_favorites_user_time` | `SELECT user_id, created_at FROM favorites WHERE user_id=?` | 查询列全部在索引中 |
| `idx_activities_user_time` | `SELECT id, type, created_at FROM activities WHERE user_id=?` | 索引覆盖 (user_id, created_at) + 聚簇 id |
| `idx_messages_recipient_time` | `SELECT id, created_at FROM messages WHERE recipient_id=?` | 收发件箱基础查询 |

##### 1.3.3.4 不建议添加的索引

以下场景**刻意不建索引**，避免维护开销大于收益：

| 表/列 | 不建索引原因 |
|:---|:---|
| `is_active`（各表） | 选择性极低（仅 TRUE/FALSE），单独索引无法有效过滤，查询优化器倾向于全表扫描 |
| `is_banned`（users, shops） | 同上，封禁用户/店铺比例极低，不适合 B+Tree 索引 |
| `is_read`（messages） | 需与 `recipient_id` 组合才有意义；当前通过 `idx_messages_recipient_time` 扫描后内存过滤 |
| `menu_items(shop_id)` | 单店铺菜单项数量极少（< 100 条），额外索引的查询加速收益极低 |
| `view_history(user_id, shop_id)` | 唯一约束 `uk_view_history` 已隐含建立索引，无需重复 |

##### 1.3.3.5 索引维护建议

| 维护项 | 方法 | 频率 |
|:---|:---|:---|
| 索引使用率监控 | 查询 `sys.schema_unused_indexes` 找出未使用索引 | 每月 |
| 索引碎片整理 | `OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB` | 每季度 |
| 慢查询分析 | 开启 `slow_query_log`，通过 `pt-query-digest` 或 `mysqldumpslow` 分析 | 每周 |
| 索引基数验证 | `SHOW INDEX FROM <table>` 查看 `Cardinality` 是否接近行数 | 每月 |

## 2. 数据库元素命名规则

### 2.1 命名总则

| 元素 | 命名规范 | 示例 | 说明 |
|:---|:---|:---|:---|
| 数据库名 | 小写蛇形（snake_case） | `foodiehub_db` | 与项目名一致 |
| **表（Table）** | 小写蛇形，复数 | `users`, `shop_comments`, `dict_data` | 表示集合语义；关联表用 `_rel` 后缀（如 `dict_rels`） |
| **字段（Column）** | 小写蛇形 | `user_id`, `created_at`, `is_active`, `view_count` | FK 列以 `_id` 结尾；布尔列以 `is_` / `has_` 开头；时间列以 `_at` / `_time` 结尾；计数列以 `_count` 结尾 |
| **主键（Primary Key）** | `PRIMARY KEY`（自增 `id`） | `id INT AUTO_INCREMENT PRIMARY KEY` | 统一使用 `id`，不设组合主键 |
| **外键（Foreign Key）** | `fk_<源表>_<目标列>` | `fk_ratings_user`, `fk_menu_shop` | 短名称，体现关联方向 |
| **唯一约束（Unique Key）** | `uk_<表>_<列1>_<列2>` | `uk_ratings_user_shop`, `uk_users_username` | 组合唯一约束列出所有参与列 |
| **索引（Index）** | `idx_<表>_<列1>_<列2>` | `idx_comments_shop_time`, `idx_oplog_operator_time` | 按表名前缀 + 关键列命名，功能性索引加 `_time`、`_status` 后缀 |
| **视图（View）** | `v_<用途>` | `v_pending_feedbacks`, `v_unread_messages` | 以 `v_` 前缀区分表与视图（*补充说明：当前未实现视图，仅为命名预留*） |
| **存储过程/函数（Procedure/Function）** | 不使用（见第 5、6 章） | — | 业务逻辑全部在应用层（Python DAO） |

### 2.2 命名示例与理由

```sql
-- 表名：蛇形复数
CREATE TABLE menu_items ( ... );       -- 菜单项表

-- 字段：蛇形，FK 后缀 _id
ALTER TABLE menu_items
  ADD COLUMN shop_id INT NOT NULL,     -- 外键列
  ADD CONSTRAINT fk_menu_shop          -- 外键约束名
    FOREIGN KEY (shop_id) REFERENCES shops(id) ON DELETE CASCADE;

-- 唯一约束
ALTER TABLE ratings
  ADD CONSTRAINT uk_ratings_user_shop  -- 反映"用户+店铺"组合唯一
    UNIQUE KEY (user_id, shop_id);

-- 索引：前缀 idx_ 表明是辅助索引
CREATE INDEX idx_comments_shop_time ON shop_comments (shop_id, created_at);
```

**命名理由**：

- **统一小写蛇形**：避免不同操作系统/DBMS 的大小写敏感差异，提高可移植性。
- **FK 列 `_id` 后缀**：一眼可分辨 FK 列与实际关联的实体，代码可读性强。
- **`is_banned` 与 `is_active` 语义解耦**：`is_banned`（管理员封禁）和 `is_active`（软删除/注销）是两个独立维度，不混用同一字段，符合 README §1.1 的设计总则。
- **冗余计数 `_count` 后缀**：`view_count`、`like_count`、`favorite_count` 等冗余字段统一 `_count` 词缀，DA/Markdown 文档中含义自明。

| `ratings` | ✅ | ✅ | ✅ | ✅ | 无特殊限制 |
| `activities` | ✅ | ✅ | ✅ | ✅ | 无特殊限制（动态为自动生成，不直接手动修改） |
| `favorites` | ✅ | ✅ | ✅ | ✅ | 无特殊限制 |
| `messages` | ✅ | ✅ | ✅ | ✅ | 可发送系统公告 |
| `images` | ✅ | ✅ | ✅ | ✅ | 多态关联，级联删除由 DAO 处理 |
| `shop_comments` | ✅ | ✅ | ✅ | ✅ | 可删除违规评论 |
| `comment_replies` | ✅ | ✅ | ✅ | ✅ | 可删除违规回复 |
| `shop_questions` | ✅ | ✅ | ✅ | ✅ | 无特殊限制 |
| `question_answers` | ✅ | ✅ | ✅ | ✅ | 无特殊限制 |

| `operation_logs` | ✅ | ❌ | ❌ | ❌ | **仅追加写入（由系统自动创建），管理员仅可查询，不可增、改、删** |

### 3.3 权限实现方式

权限控制采用**应用层（Python FastAPI + Tortoise ORM）实现**，不依赖数据库级 GRANT 语句：

1. **认证层（JWT Token）**：登录后签发 JWT，`role` 字段嵌入 Token payload，所有请求携带 Token 经中间件校验。
2. **授权层（FastAPI Dependency）**：每个 API 路由使用 `Depends(get_current_admin)` 依赖注入，验证 `role == 1`。
3. **软删除过滤**：ORM 的 BaseModel 默认过滤 `is_active=True`，管理员通过特殊查询参数 `?include_deleted=true` 查看软删除记录。

*（补充说明：若后续需要数据库级权限控制，可创建 MySQL 用户 `admin_foodie` 并对其执行 `GRANT ALL ON foodiehub_db.* TO 'admin_foodie'@'localhost'`，但当前课程设计阶段暂不实施。)*

## 4. 数据检索与修改方法

### 4.1 总体方案

本系统在应用程序中通过编写代码、使用 SQL 语句完成数据的检索与修改。具体采用以下两种方式：

| 方式 | 工具 | 适用场景 |
|:---|:---|:---|
| **ORM 查询构造器** | Tortoise ORM（Python async ORM） | 90% 的常规 CRUD 操作——单表查询、外键关联预加载（`.prefetch_related()`）、分页、排序、更新冗余字段 |
| **RAW SQL** | Tortoise `.raw()` / `connection.execute_query()` | 复杂聚合查询、跨表统计、批量异步更新、性能敏感的热路径 |

### 4.2 参数化查询策略

无论 ORM 还是 raw SQL，所有用户输入均通过**参数化绑定**传递，杜绝 SQL 注入：

- **ORM 方式**：Tortoise 内部自动使用参数化查询（底层为 `aiomysql` 的参数化占位符）。
- **Raw SQL 方式**：使用 `connection.execute_query(sql, [param1, param2])` 方式传参，禁止直接拼接字符串。

### 4.3 ORM 查询示例（常见检索与修改）

#### 示例 1：按店铺名称模糊搜索（带标签预加载）

```python
# 检索：按店铺名称搜索 + 预加载标签体系
from models import Shops, DictRel, DictData, DictTypes

async def search_shops(keyword: str, page: int = 1, page_size: int = 20):
    """
    参数化查询——ORM 自动处理参数绑定
    """
    shops = await Shops.filter(
        name__icontains=keyword,   # LIKE '%keyword%'
        is_active=True,
        is_banned=False
    ).offset((page - 1) * page_size).limit(page_size)

    # 批量预加载标签（避免 N+1 问题）
    shop_ids = [s.id for s in shops]
    rels = await DictRel.filter(
        entity_type='shop',
        entity_id__in=shop_ids
    ).prefetch_related('dict_data__dict_type')

    return shops, rels
```

> **说明**：`name__icontains` 是 Tortoise ORM 的查询构造器语法，底层映射为 `WHERE name LIKE '%keyword%'`，keyword 通过参数化绑定传入，安全无注入风险。

#### 示例 2：用户收藏切换（Toggle 操作）

```python
# 修改：收藏/取消收藏（软删除实现，保留操作历史）
async def toggle_favorite(user_id: int, shop_id: int) -> bool:
    """
    首次收藏 → INSERT；取消收藏 → is_active=False；再次收藏 → is_active=True
    """
    existing = await Favorites.filter(
        user_id=user_id,
        shop_id=shop_id
    ).first()

    if existing:
        # Toggle: 反向 is_active
        existing.is_active = not existing.is_active
        await existing.save()
        new_state = existing.is_active
    else:
        # 首次收藏
        await Favorites.create(user_id=user_id, shop_id=shop_id, is_active=True)
        new_state = True

    # 更新 shops.favorite_count 冗余字段（在 DAO 层手动同步）
    delta = 1 if new_state else -1
    await Shops.filter(id=shop_id).update(
        favorite_count=Shops.favorite_count + delta
    )

    return new_state
```

#### 示例 3：用户时间线分页查询（索引优化）

```python
# 检索：按创建时间倒序获取用户动态（利用索引 idx_activities_user_time）
async def get_user_activities(user_id: int, page: int = 1):
```

### 4.4 Raw SQL 示例（复杂聚合/批量操作）

#### 示例 4：按日期范围统计用户操作行为

```python
# 复杂聚合检索：统计某日期范围内的用户行为分布
from tortoise import connections

async def get_user_behavior_stats(start_date: str, end_date: str):
    conn = connections.get("default")
    sql = """
        SELECT action, COUNT(*) AS cnt
        FROM operation_logs
        WHERE created_at >= %s
          AND created_at < %s
          AND is_active = TRUE
        GROUP BY action
        ORDER BY cnt DESC
    """
    # 参数化绑定（防 SQL 注入）
    rows = await conn.execute_query_dict(sql, [start_date, end_date])
    return rows
```

#### 示例 5：批量更新冗余计数（高效写操作）

```python
# 批量修改：店铺合并后更新所有关联评论的冗余 reply_count
async def batch_update_reply_count(comment_ids: list[int]):
    """
    使用子查询一次性更新所有评论的 reply_count
    """
    conn = connections.get("default")
    sql = """
        UPDATE shop_comments AS sc
        SET sc.reply_count = (
            SELECT COUNT(*) FROM comment_replies AS cr
            WHERE cr.comment_id = sc.id AND cr.is_active = TRUE
        )
        WHERE sc.id IN %s
    """
    await conn.execute_query(sql, [tuple(comment_ids)])
```

### 4.5 数据修改方式总结

| 操作类型 | 实现方式 | 说明 |
|:---|:---|:---|
| 单行 INSERT | `Model.create(**kwargs)` | Tortoise ORM |
| 批量 INSERT | `Model.bulk_create(objects)` | 用于初始化数据/批量导入 |
| 单行 UPDATE | `instance.save()` | 修改内存中的 ORM 对象后 save |
| 条件批量 UPDATE | `Model.filter(...).update(...)` | 利用 `F()` 表达式实现原子自增/自减 |
| 软删除 DELETE | `Model.filter(...).update(is_active=False)` | 全表使用逻辑删除，不执行物理 DELETE |
| 复杂聚合/统计 | `connection.execute_query_dict(sql, params)` | Raw SQL + 参数化绑定 |
| 事务 | `async with in_transaction(): ...` | 确保多表写操作的原子性（如评分 + 更新 average_rating） |

## 5. 触发器使用情况

### 5.1 决策：不使用触发器

在本次课程设计中，**未使用任何数据库触发器（Trigger）**。理由如下：

| 不使用触发器的原因 | 详细说明 |
|:---|:---|
| **1. 业务逻辑在应用层维护** | 数据的验证、级联更新（如评分后更新 `average_rating`、收藏后更新 `favorite_count`）、软删除级联等操作，全部在 Python DAO（数据访问对象）层实现。应用层代码有完整的版本控制和单元测试，比数据库触发器更易调试和维护。 |
| **2. 软删除模型的特殊性** | 系统大量使用 `is_active` 软删除字段。触发器无法处理"软删除级联"——例如，当 `shop_comments.is_active=False` 时，需要同步使关联的 `images` 记录 `is_active=False`，这需要应用层判断逻辑，触发器无法优雅实现。 |
| **3. 避免隐式行为** | 触发器在后台自动执行，开发者不易察觉其存在和效果。当出现数据不一致时，排查触发器副作用非常困难。将逻辑显式编码在 DAO 层，代码意图清晰、可审计。 |
| **4. ORM 兼容性** | Tortoise ORM（以及大多数异步 ORM）对数据库触发器的支持有限。触发器的行为不会被 ORM 的变更追踪感知，可能导致缓存不一致或重复计算。 |
| **5. 跨表操作的事务控制** | 涉及多表的写操作（如"提交评论+上传图片+创建动态+发送通知"）需要统一的事务边界。应用层事务管理（`async with in_transaction()`）比分散在多个触发器中更容易协调。 |

### 5.2 替代方案

原可交由触发器处理的常见场景，本系统采用以下替代方案：

| 触发器典型场景 | 本系统的替代方案 |
|:---|:---|
| 评分后自动更新店铺平均分 | DAO 层 `update_rating()` 函数内，计算新平均值并原子更新 `shops.average_rating` |
| 评论后自动 +1 `comment_count` | DAO 层 `create_comment()` 函数内，使用 `F('comment_count') + 1` 原子更新 |
| 软删除图片后级联清理 | DAO 层 `delete_entity()` 统一函数，同步软删除关联 `images` 记录 |
| 操作自动记录日志 | Service 层在每个业务方法末尾手动调用 `create_operation_log()` |

## 6. 存储过程与自定义函数

### 6.1 决策：不使用存储过程

本系统**未使用任何数据库存储过程（Stored Procedure）**，所有对数据库的增、删、改、查操作通过**应用层 Python 异步函数（DAO + Service 层）**封装实现。

### 6.2 DAO 层函数设计

DAO（Data Access Object）层是数据库操作的唯一入口，每个函数封装一条或多条 SQL/ORM 操作，并提供统一的错误处理与事务管理。

#### 6.2.1 设计目的

| 目的 | 说明 |
|:---|:---|
| **接口单一性** | 每个函数只做一件事（单一职责），如 `get_shop_by_id()` 仅查询店铺 |
| **复用性** | Service 层的多个业务逻辑可复用同一个 DAO 函数 |
| **可测试性** | 每个 DAO 函数可独立进行单元测试（mock 数据库连接） |
| **事务边界清晰** | 复杂的跨表操作在 DAO 层内部管理事务（`in_transaction()` 上下文） |
| **软删除透明化** | 所有查询默认过滤 `is_active=True`，调用方无需关心软删除细节 |

#### 6.2.2 命名规范

| 前缀 | 操作 | 示例 |
|:---|:---|:---|
| `get_` | 单条查询 | `get_shop_by_id(shop_id)` |
| `list_` | 多条查询 / 分页列表 | `list_shops_by_category(dict_data_id, page)` |
| `create_` | 插入 | `create_comment(user_id, shop_id, content)` |
| `update_` | 更新（含部分字段） | `update_rating(user_id, shop_id, score)` |
| `delete_` / `soft_delete_` | 软删除 | `soft_delete_comment(comment_id)` |
| `toggle_` | 开关切换 | `toggle_favorite(user_id, shop_id)` |
| `count_` | 计数统计 | `count_pending_feedbacks()` |

#### 6.2.3 DAO 函数示例

```python
# ----------------------------------------------------------------
#  例 1：店铺 CRUD 封装
# ----------------------------------------------------------------

async def get_shop_by_id(shop_id: int) -> Optional[Shops]:
    """根据 ID 获取店铺（仅返回 is_active=True 且 is_banned=False）"""
    return await Shops.filter(
        id=shop_id, is_active=True, is_banned=False
    ).first()


async def list_shops_with_tags(page: int = 1, page_size: int = 20) -> list[Shops]:
    """分页获取店铺列表（含标签预加载，避免 N+1 查询）"""
    shops = await Shops.filter(
        is_active=True, is_banned=False
    ).order_by('-view_count').offset(
        (page - 1) * page_size
    ).limit(page_size)

    # 批量预加载标签
    shop_ids = [s.id for s in shops]
    rels = await DictRel.filter(
        entity_type='shop', entity_id__in=shop_ids
    ).prefetch_related('dict_data__dict_type')

    return shops


async def create_shop(name: str, user_id: int) -> Shops:
    """创建店铺 + 自动生成动态 + 写入日志"""
    async with in_transaction():
        shop = await Shops.create(name=name)
        # 生成动态（提醒关注者）
        await Activities.create(
            user_id=user_id, type='add_shop',
            target_id=shop.id, target_type='shop',
            content=f'新增了店铺"{name}"', shop_id=shop.id
        )
        # 写入操作日志
        await create_operation_log(
            operator_id=user_id, action='add_shop',
            target_type='shop', target_id=shop.id
        )
        return shop


# ----------------------------------------------------------------
#  例 2：评分 CRUD 封装
# ----------------------------------------------------------------

async def upsert_rating(user_id: int, shop_id: int, score: int) -> Ratings:
    """
    创建或更新评分（每个用户对每个店铺仅一条记录）
    同时更新 shops.average_rating 冗余字段
    """
    async with in_transaction():
        rating, created = await Ratings.get_or_create(
            user_id=user_id, shop_id=shop_id,
            defaults={'score': score}
        )
        if not created:
            rating.score = score
            await rating.save()

        # 重新计算该店铺平均分（原子操作）
        from tortoise.functions import Avg
        avg_result = await Ratings.filter(
            shop_id=shop_id, is_active=True
        ).annotate(avg=Avg('score')).first().values('avg')

        await Shops.filter(id=shop_id).update(
            average_rating=round(avg_result['avg'], 2) if avg_result['avg'] else 0.0
        )

        return rating


# ----------------------------------------------------------------
#  例 3：软删除级联封装
# ----------------------------------------------------------------

async def soft_delete_shop_comment(comment_id: int) -> None:
    """
    软删除一级评论 + 级联软删除其二级回复 + 关联图片
    """
    async with in_transaction():
        # 软删除一级评论
        await ShopComments.filter(id=comment_id).update(is_active=False)

        # 软删除所有二级回复
        await CommentReplies.filter(comment_id=comment_id).update(is_active=False)

        # 软删除关联图片（多态关联，无 FK 约束）
        await Images.filter(
            entity_type__in=['shop_comment', 'comment_reply'],
            entity_id__in=[comment_id]  # 此处需扩展为回复 ID 列表
        ).update(is_active=False)
```

### 6.3 与存储过程/数据库自定义函数的对比

| 维度 | 存储过程（未采用） | Python DAO 函数（已采用） |
|:---|:---|:---|
| **语言** | SQL 方言（MySQL PL/SQL） | Python 3.12+（async/await） |
| **版本控制** | 难以 diff / code review | Git 友好，可见完整 diff |
| **调试** | 调试困难，需专门工具 | PyCharm / VSCode 断点调试 |
| **单元测试** | 困难 | pytest + mock 无依赖 |
| **ORM 集成** | 需单独调用 | 与 Tortoise ORM 无缝集成 |
| **事务管理** | 存储过程内部 COMMIT/ROLLBACK | Python `async with in_transaction()` 弹性控制 |
| **业务逻辑复杂度** | SQL 编写复杂逻辑困难 | Python 可引入三方库、复杂算法 |
| **移植性** | 绑定特定 DBMS（MySQL） | 切换 ORM 后端即可更换数据库（如 PostgreSQL） |
| **性能** | 减少网络往返，批量操作更快 | 多次通信（但 ORM 可批量 prefetch 优化） |

**总体结论**：对于以 **Python 后端为核心**、**逻辑复杂度中等**的 Web 应用，采用 DAO 层函数封装优于存储过程。其优势在于**代码可维护性、可测试性和开发效率**，且 ORM 的自动查询构造器已能覆盖 90% 以上的数据操作。
