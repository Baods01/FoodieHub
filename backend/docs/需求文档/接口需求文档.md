# 后端接口需求文档

> **面向**：后端开发人员  
> **目的**：梳理当前 API 与前端实际需求的差距，提出接口补齐 / 修正建议  
> **依据**：前端设计文档（`/src/admin/`、`/src/pages/`）、OpenAPI 规范（`openapi.json`）、REASONIX.md 设计理念

---

## 一、平台设计理念回顾

| 原则 | 说明 |
|:---|:---|
| 游客友好 | 所有读操作无需登录，写操作触发登录引导 |
| 乐观更新 | 收藏/点赞/评分前端先改 UI 再异步确认 |
| 轻量店铺 | 店铺创建仅三必填（名称、品类、区域），即时上线 |
| 社区自净 | 评论/问答补全信息，举报触发管理员后置仲裁 |

---

## 二、核心问题综述

当前 OpenAPI 接口存在以下 **5 类问题**：

| 编号 | 问题 | 严重性 |
|:---|:---|:---|
| 1 | **字典数据无独立查询接口** — 首页筛选器无法预加载品类/区域/就餐方式选项 | **严重** |
| 2 | **收藏/历史列表响应缺少店铺信息** — 前端展示需要店铺名、评分、封面图等，无法通过单独 request 逐一查询 | **严重** |
| 3 | **店铺响应中的 category/area 只有 code 没有 name** — ShopResponse 中 `dict_data` 字段已包含 code+name 映射，但字段分散 | 中 |
| 4 | **用户动态/活动接口未在 OpenAPI 中定义完整 schema** — 响应字段不明确 | 低 |
| 5 | **部分接口路径命名不一致** — `/user/history/` vs `/users/me/*`、收藏模块多个冗余端点 | 低 |

---

## 三、逐接口需求详述

### 3.1 🚨 字典数据接口（缺失 — 最高优先级）

**场景**：首页加载时，筛选栏需要展示"品类"、"区域"、"就餐方式"三个下拉框，每个下拉框的选项列表必须在用户输入前预加载完毕。

**现状**：OpenAPI 中**无**字典数据的独立查询接口。字典数据仅作为 `ShopResponse.dict_data` 嵌入在店铺响应中。

**需求**：

```
新增接口: GET /dict-data
```

| 查询参数 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| `type_code` | string | 否 | 字典类型编码，如 `category`、`location_type`、`dining_method`。不传则返回所有类型及其数据 |

**响应格式**：

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "type": {
        "code": "category",
        "name": "品类"
      },
      "items": [
        { "id": 1, "code": "hotpot", "name": "火锅", "extra": null },
        { "id": 2, "code": "barbecue", "name": "烧烤/烤肉", "extra": null }
      ]
    },
    {
      "type": {
        "code": "dining_method",
        "name": "就餐方式"
      },
      "items": [
        { "id": 20, "code": "dine_in", "name": "堂食", "extra": null },
        { "id": 21, "code": "pickup", "name": "自取", "extra": null },
        { "id": 22, "code": "delivery", "name": "外卖", "extra": null }
      ]
    }
  ]
}
```

**为什么不能从店铺列表提取**：
- 某个品类可能当前无店铺，但仍需在筛选中显示
- 前端不应依赖已有数据推导元数据
- 字典是平台的基础数据，理应有独立 API

---

### 3.2 🚨 收藏列表接口（响应字段不足）

**场景**：用户打开收藏夹 `/favorites`，每行显示店铺封面图、名称、品类、区域、评分、收藏数。

**现状**：`GET /favorites/user` 的响应只包含收藏关系数据，不包含被收藏店铺的基本信息。

**需求**：收藏列表每一项需**一并返回**被收藏店铺的以下字段：

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `shop.id` | int | 店铺 ID |
| `shop.name` | string | 店铺名称 |
| `shop.category` | string | 品类中文名（如 "火锅"） |
| `shop.area` | string | 区域中文名（如 "华农西门"） |
| `shop.average_rating` | number | 平均评分 |
| `shop.favorite_count` | int | 收藏总数 |
| `shop.cover_image` | string|null | 封面图 URL |
| `favorited_at` | datetime | 收藏时间（用于排序） |

**同样适用于**：
- `GET /user/history/` — 历史列表每项需一并返回店铺基本信息（同上）
- `GET /messages` — 消息列表若关联到店铺/评论，需返回关联对象的基本摘要

---

### 3.3 店铺列表接口（基本可用，需确认分页格式）

**场景**：首页展示店铺卡片网格，每页 12 张，支持无限滚动。

**需要确认**：`GET /shops/` 返回的分页数据格式。

**期望格式**（react-admin 兼容）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [
      { "id": 1, "name": "陈记糖水铺", "dict_data": [...], "average_rating": "4.5", ... }
    ],
    "total": 236,
    "page": 1,
    "page_size": 20
  }
}
```

**关键点**：
- `total` 字段必须顶置，不能藏在 `shops` 内部
- `average_rating` 当前类型为 `string`（带正则），建议改为 `number`
- `category`/`area` 建议增加中文名常量字段，不要只靠 `dict_data[]` 前端遍历

---

### 3.4 店铺详情接口（基本可用）

**场景**：店铺详情页展示轮播图、评分分布、评论区、问答区、菜单、相册。

`GET /shops/{id}` 的 `ShopResponse` 已包含：
- ✅ 基本信息（name, description, average_rating 等）
- ✅ `dict_data`（类别/区域/就餐方式字典映射）
- ✅ `menu_items`（菜单项）
- ✅ `images`（图片列表）
- ✅ `rating_distribution`（评分分布）
- ✅ `is_favorited`（当前用户是否已收藏）
- ✅ `user_rating`（当前用户的评分）

**建议修正**：

| 字段 | 现状 | 建议 |
|:---|:---|:---|
| `average_rating` | string（`"4.5"`） | number（`4.5`） |
| `shop.category_name` | 不存在 | 新增：直接从 `dict_data` 中提取对应 name |
| `shop.area_name` | 不存在 | 同上 |
| `menu_items[].image` | 不确定 | 需确认是否有图片字段 |

### 3.5 认证接口（基本可用）

| 端点 | 方法 | 状态 |
|:---|:---|:---|
| `POST /users/login` | OAuth2 表单 | ✅ 可用 |
| `POST /users/login-phone` | JSON | ✅ 可用 |
| `POST /users/login-email` | JSON | ✅ 可用 |
| `POST /users/register` | JSON | ✅ 可用 |
| `GET /users/me` | Bearer Token | ✅ 可用 |

**需要确认**：`POST /users/login` 返回的 `access_token` 是否同时返回用户基本信息（id, username, role, avatar 等），避免额外 `GET /users/me` 调用。

---

### 3.6 收藏切换接口（基本可用，建议简化）

**现状**：存在三个端点：
- `POST /favorites/toggle` — 切换收藏
- `POST /favorites/favorite` — 仅收藏
- `POST /favorites/unfavorite` — 仅取消
- `GET /favorites/shop/{shop_id}/count` — 获取收藏数

**建议**：保留 `POST /favorites/toggle` 和 `GET /favorites/shop/{shop_id}/count`，移除冗余的 `favorite` / `unfavorite`。

---

### 3.7 评论接口（基本可用，需确认格式）

**现状**：
- `GET /shops/{id}/comments` — 获取评论列表（支持 `comment_type` 筛选：comment / question）
- `POST /shops/{id}/comments` — 创建评论/提问
- `GET /shops/{id}/comments/{comment_id}/replies` — 获取回复
- `POST /comments/like` — 点赞评论
- `GET /comments/{comment_id}/like-count` — 点赞数

**需要确认**：评论列表的响应是否已包含：
- 评论者用户名、头像
- 点赞数
- 当前用户是否已点赞
- 子回复数量

---

### 3.8 用户动态接口（需确认）

**现状**：
- `GET /users/me/activities` — 自己动态
- `GET /users/{user_id}/activities` — 他人动态

**需要确认**：每条动态是否包含：
- `type`（rating / comment / favorite / add_shop / question）
- `content`（文字描述）
- `shop_id`（关联店铺 ID，供前端跳转）
- `extra`（附加数据，如评分星级 `{ score: 4 }`）
- `created_at`

---

### 3.9 消息通知接口

**现状**：`GET /messages`、`POST /messages/mark-read`、`POST /messages/mark-all-read` 等

**需要确认**：每条消息是否包含：
- `type`（reply / like / announcement）
- `title`（标题）
- `description`（摘要）
- `shop_id`（关联店铺，供前端跳转）
- `is_read`
- `created_at`

---

### 3.10 管理后台接口（基本可用）

管理后台 6 个模块所需接口均已存在于 OpenAPI 中，无缺失。

**仅需确认**：
- `GET /admin/users` 的分页格式（同上）
- `GET /admin/logs` 的筛选参数是否支持时间范围
- `GET /admin/stats/overview` 在 `days` 参数下 `daily_stats` 的实际返回

## 四、优先级排序

| 优先级 | 问题 | 影响页面 |
|:---:|:---|:---|
| P0 | 新增 `GET /dict-data` 接口 | 首页筛选、上传店铺表单 |
| P0 | 收藏列表/历史列表返回店铺详情 | 收藏夹、浏览历史 |
| P1 | `average_rating` 改为 number | 首页、详情页 |
| P1 | 店铺列表分页格式确认 | 首页 |
| P2 | 收藏端点简化（合并 redundant APIs） | 收藏模块 |
| P2 | 评论/动态/消息响应字段补充 | 详情页、个人中心、消息中心 |
